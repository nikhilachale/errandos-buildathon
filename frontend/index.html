01 / Request

Describe the errand.

“Add milk, eggs and atta to my usual grocery order.” The conversational layer interprets the request; it does not receive provider credentials or raw device controls.

02 / Review

See the exact terms.

Errands prepares a proposal for review. Preparation is read-only: it never places the order.

ItemsQuantitiesPricesFeesAddress labelPaymentETAExpiryProvider
03 / Approve

Approve this proposal—once.

Approval binds only the terms on screen. If a material detail changes, the approval is invalidated and a new proposal is required.

04 / Resolve

Know what actually happened.

The planned coordinator attempts the final provider action at most once. It returns a verified receipt, a blocked state, or an ambiguous state that needs read-only reconciliation.

Safety is the product

A clear boundary before anything changes.

01
Prepare, then pause.

Reading provider state and preparing exact terms never places an order.

02
Bind approval to terms.

A changed price, item, fee, address, payment mode, ETA, expiry, or provider requires a new proposal.

03
Attempt the final action once.

Each commit uses an idempotency key, with dispatching made durable before the attempt.

04
Never turn uncertainty into success.

Timeouts and unknown outcomes become ambiguous; reconciliation uses read-only checks.

05
Verify the outcome.

Success requires a provider reference or receipt—not an optimistic interface message.

When the provider cannot confirm what happened, Errands says so plainly—and checks without repeating the action.

Architecture

A narrow surface between conversation and consequence.

The conversational agent can describe intent and call narrow, typed tools. It cannot access credentials, provider sessions, or raw device controls.
